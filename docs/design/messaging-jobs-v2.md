# Messaging and durable jobs: design

An alternative to PR #533, built from the review of that PR. Goals, in priority order:

1. **A transport or job store is easy to write**, and a conformance suite proves it works.
2. **A fantastic developer experience**: each common task needs a handful of concepts, and mistakes fail early with clear errors.
3. **Nothing breaks.** `IQueue<T>`, `IMessageBus` and the existing jobs stay as they are, so providers and apps move one piece at a time.

Decisions: side-by-side with the legacy APIs for v14 (delete them in v15); store-based durable jobs; core owns handler registration (Mediator can build on it); pub/sub works on every broker, and queues are expressible on Kafka through the same contract.

## Layers

```
  Application        IMessageClient   IMessageHandler<T>   IJobClient   IJobHandler<TArgs> / IJobHandler
  ───────────────────────────────────────────────────────────────────────────────────────
  Foundatio core     routing · serialization · retries · dead letters · concurrency · leases
                     delays · shutdown drain · tracing · metrics · CRON · startup gate
  ───────────────────────────────────────────────────────────────────────────────────────
  Provider SPI       IMessageTransport + IMessageReceiver (9 methods)    IJobStore (12 members, 2 with defaults)
```

The provider SPI is `[Experimental("FOUNDATIO0001")]` in v14, because it has been tried against Service Bus only on its emulator and may change in a minor release. That covers `IMessageTransport`, `IMessageReceiver`, `IncomingMessage`, `OutgoingMessage`, `MessageDestination`, `ReceiverOptions`, `MessageSize`, the lease-lost and receiver-faulted exceptions, `IJobStore` with `JobClaimRequest`, `JobCompletion`, `JobLeaseStatus` and `JobInfo`, `SettlementBatcher<TEntry>` (the shared group commit for settlements), and the conformance suites. The diagnostic is an error by default, so provider projects suppress it with `NoWarn`. App code that uses the builders, the provider helpers, the clients, the handlers and the test harness never sees it: the concrete transports and stores implement the SPI explicitly, so their public surface is constructors, options, `Capabilities` and the in-memory test helpers, and each provider test project checks that no public unmarked type exposes the SPI. `TransportCapabilities` (the harness and the in-memory transport take it) stays unmarked; `MessageSource`, `MessageSourceKind`, `MessageSourceStats` (`IMessageAdmin` takes them) and `MessageTooLargeException` (apps catch it) live in `Foundatio.Messaging`, so apps never import the SPI namespace.

Messaging and jobs are independent: neither depends on the other's contracts. They interact only through ambient correlation (a job enqueued from a handler inherits the message's correlation id, and vice versa).

## Transport contract

| Member | Purpose |
|---|---|
| `Capabilities` | What the broker does natively. Core adapts. |
| `SendAsync(destination, messages)` | To a queue, to a topic's subscriptions, or to one durable subscription. Batch-first. |
| `CreateReceiverAsync(source, options)` | Queue, durable subscription, instance subscription, or a dead-letter queue. |
| `DeleteAsync(source)` | Remove a queue or subscription (with its dead letters), or only a source's dead letters. |
| `GetStatsAsync(source)` | Approximate queued, delayed, in-flight and dead-lettered counts for dashboards; each null when the broker can't tell. |
| `ReceiveAsync(max, maxWait)` | Leased deliveries. |
| `CompleteAsync` / `AbandonAsync(delay)` / `DeadLetterAsync(reason)` / `RenewAsync` | Settlement. |

A transport whose broker decides the lease (Service Bus sets a lock duration per entity) sets `IncomingMessage.LeaseExpiresAt`, and core renews a third of the way through the remaining lease instead of by its own `LeaseDuration`.

Everything else is core: there are no optional capability interfaces to discover, no push/pull split, no provisioning API and no outcome model in the SPI; the only read-side member is `GetStatsAsync`, whose counts are data the transport reads from the broker, never state it keeps for the purpose. `TransportCapabilities` (send, publish and retry delay limits, batch/message/lease limits, concurrent receives, read-ahead, lease expiration, ordered groups and whether a group has at most one message out at a time, deduplication) is data, not interfaces, and the conformance suite reads it to decide which tests apply.

How brokers map:

| Broker | Queue | Topic / subscription | Instance subscription | Delay | Groups |
|---|---|---|---|---|---|
| Redis Streams | stream + group | fan-out into per-subscription streams | stream on its topic's slot, with heartbeat, swept when stale | sorted set | group hash: one outstanding message per group |
| SQS / SNS | queue | SNS topic → SQS queue | per-instance queue, tagged and swept | 13 days (15 min native on standard queues, the rest hidden) | FIFO message groups |
| Service Bus | queue (`queue.{name}`) | topic subscription, with a rule for sends to one subscription | AutoDeleteOnIdle subscription, deleted on dispose | scheduled messages; retries are scheduled copies | sessions; delayed grouped messages held by their session's receiver |
| RabbitMQ | quorum queue | fanout exchange → quorum queue per subscription | exclusive auto-delete queue | 28 shared delay levels: fixed-TTL queues dead-lettering into the next, then a landing queue per delayed target | — |
| Kafka | topic + consumer group, completion-tracked offsets | group per subscription, plus its own retry topic | every partition read from the end, no group | delay-tier topics and a forwarder | partition key |
| Storage Queues | queue | queue per subscription (queue metadata), publish lists them | queue per instance, swept when stale | visibility timeout, 7 days (less with `MessageTimeToLive`) | — |

The Kafka transport sets `LeaseExpiration = false`, commits the lowest unfinished offset per partition, and copies abandoned messages to the source's own topic. Brokers with push client libraries buffer into a bounded channel inside the receiver.

Proof: `MessageTransportTestsBase` (79 tests) plus `JobStoreTestsBase` (45 tests). A provider test class is one override, plus `CreatePeerTransport` when a second transport over the same backend, which the suite uses as another process, needs different setup. The suite fails a transport that keeps group order only within one receiver, settles by message id and ignores receipts, lets a stale complete remove a message another receiver holds (only SQS, which can't tell, overrides `StaleCompleteMayRemoveTheMessage`), reports a `LeaseExpiresAt` outside the granted lease, leaves a receiver deaf after its queue or subscription is deleted, or only polls instead of waking a waiting receive. Contract points the suite pins down: a send to one subscription creates it, as opening a receiver does; header names are case-sensitive; ids may hold any character, U+0000 included.

A PostgreSQL transport written in round 7 from the provider guide alone (not in this repo) passed the 69-test suite on its first run, about 35 minutes after its author started reading. Hand mutation then found 16 contract violations the suite let through; the checks above kill 12 of them, and it was the third transport to write its own settlement group commit, which is why `SettlementBatcher<TEntry>` moved into core.

### Redis proof

A Redis Streams transport and a Redis job store (`src/Foundatio.Redis`, which came into this repo with its history in #603) were written against this contract, without changing core:

- **Transport:** about 1,060 lines of C# and 460 of Lua.
  - Each source is one stream and consumer group, plus sorted sets for leases and delays (scored by Redis `TIME`), and a hash for ordered groups.
  - Each source's keys share a hash tag, and every key a script touches is declared, so each operation is one atomic script under Redis Cluster.
  - Publishing copies a message into every instance subscription with one script on the topic's slot (a topic's instance subscriptions share its hash tag), then into each durable subscription with one script each, so a slow subscriber never blocks the publisher. The script checks the publisher's list of instances against the live one and returns the live list when they differ, so a new instance subscription never misses a message published after its receiver was returned.
  - A receive that drains its source with room to spare registers its receiver as idle; each message made available wakes one idle receiver, most recently busy first, over its own channel published from the script (`SPUBLISH` on Redis Cluster 7+, `PUBLISH` otherwise), so delivery across processes takes about 1 ms; polling is the fallback. A receiver woken while no receive is running (a processor that reads ahead may wait for room after a short receive) passes the wake-up to the next idle receiver after 5 ms (`MessageTransport.Wake.lua`). A delayed abandon wakes only its own receiver. Concurrent completes on a receiver share one script, through `SettlementBatcher`. Declares `ReceiveAhead` and `OneOutstandingPerGroup` (the group hash hands out one message of a group at a time), so read-ahead batches even at one handler: 62.6k msg/s at concurrency 1 against 71k for raw StackExchange.Redis, from 14.2k.
  - Reads and delayed-message promotion stop at about 8 MiB per call. While the messages it reads are 4 KiB or smaller, a receive sizes the unread entries with `XRANGE` and claims all that fit in one `XREADGROUP` (30,005 stream reads per 30k messages became 949). Dead letters can be bounded by `DeadLetterMaxLength` or `DeadLetterRetention`.
  - Instance subscriptions use heartbeats (every sixth of the timeout) and are swept when stale; a receiver that finds its subscription swept restores it and warns.
  - A durable subscription whose stream or group is gone (deleted, or lost to a restart without persistence, a failover before replication or a flush) re-registers with its topic, warns and faults (`MessageReceiverFaultedException`) on its next receive, so core replaces it with a receiver on the recreated stream; it also re-registers every 5 s while it receives, because the topic's subscription list lives on another slot and can be lost on its own. Messages published meanwhile are lost (10 in the chaos restart, against every later publish before the fix), and a publisher warns once when a topic it saw subscriptions on has none left.
  - Broker and connection errors surface as `MessageBusException`, as on the other transports.
  - Redis must not evict the transport's keys (`maxmemory-policy noeviction`); a group whose outstanding message was evicted is released with a warning.
- **Job store:** about 410 lines of C# and 230 of Lua. One hash per job, sorted sets per name for queued and running jobs, and lexicographic indexes for queries. Every key is declared, so claims take two scripts (list candidates, then claim); a worker claims one job per free slot in one `ClaimBatchAsync` (with a 1 ms round trip, 825 jobs/s at 64 slots became 11,750). Immediate and delayed jobs become available by Redis `TIME`, so a producer's clock skew doesn't move them.
- **Results:** transport 78 tests (the suite plus Redis-specific ones) on a Redis 8 cluster, standalone Redis 8 and 6.2, and Valkey 8.1; job store 31/31 on a Redis 8 cluster and on Dragonfly.

The implementer's friction notes were folded back into the contract:

- Names are validated where they are created.
- These are now documented:
  - thread safety and what disposing the transport does;
  - that `DeliverAt` comes from the sender's clock;
  - deduplication scope and `EnqueuedAt`;
  - which fields `CreateAsync` keeps;
  - renewing after a lease expires but before another worker reclaims the job.
- `JobQuery.Validate` is public.
- The CRON overlap check is one read instead of a query.
- New conformance tests cover stale receipts, delivery count after a receiver is disposed, longest-due across names, renew-after-expiry and deleting a running job.

### AWS proof

An SQS/SNS transport was written in `src/Foundatio.AWS`, about 1,400 lines, also without changing core:

- **Mapping:**
  - queues → SQS queues;
  - topics → SNS topics with raw delivery into one SQS queue per durable subscription;
  - instance subscriptions → per-receiver queues, heartbeat-tagged, deleted on dispose and swept when stale;
  - dead letters → a per-source queue with 14-day retention, copy then delete so the reason is kept.
- **Leases:** visibility timeout; stale receipts map to `MessageLeaseLostException`.
- **Envelope:** headers, id, group and delivery time travel in one binary message attribute (SQS and SNS allow 10). A valid UTF-8 body is sent as-is; any other body travels in the attribute, which SQS counts by raw bytes, so nothing grows in transit. Foreign bodies are read as-is.
- **Names:** sanitized and hashed when changed, so distinct names never collide. Queue policies are merged, not overwritten.
- **Delays:** `MaxDelay` and `MaxPublishDelay` are 13 days. Standard queues delay a send natively for its first 15 minutes; the rest, delayed publishes and FIFO delays are hidden by the receiver in 11-hour steps, within the 12 hours SQS allows from a receive. On a standard queue with 50,000 or more messages in flight, an early message is re-sent with a native delay instead of hidden. Receivers re-read the in-flight count after every 1,000 hides and at least once a minute, so receivers hiding a burst together stop near 50,000 plus 1,000 each. A receive refused with `OverLimit` returns empty; the receiver then re-sends early messages for a minute and releases its last 1,000 hides.
- **Concurrent receives:** receivers declare `MaxConcurrentReceives` = 16 and `ReceiveAhead`, since one receive returns at most 10 messages; idle, only one long poll stays open (measured on Floci only).
- **Settlement:** completes, renewals and abandons are coalesced per receiver into `DeleteMessageBatch`/`ChangeMessageVisibilityBatch` calls of up to 10, as a group commit (`SettlementBatcher`, now in core): a lone message goes out at once, and entries queue only while a call is in flight. Each receive's early, held-back and discarded messages take one batch call each. At 64 handlers that is about 0.25 requests per message, against 1.12 with a call per message; at one handler 0.26 deletes per message (7.5k msg/s, raw SDK 11.5k), since read-ahead asks for full batches and settlements up to a receive batch may wait without their slots.
- **Deleted subscriptions:** an idle subscription receiver checks its queue policy every 5 s (one `GetQueueAttributes`) and faults once its topic can no longer send to it, so a receiver is never left deaf.
- **Dispose:** a cancelled receive returns at once but lets its long poll run out (at most 20 s) and makes whatever it got visible again, so a disposed receiver never hides messages for a lease (seen on Floci; the AWS docs don't say whether real SQS hands messages to an abandoned request).
- **Groups:** `Fifo = true` uses FIFO queues and topics and declares `OrderedGroups` and `Deduplication`. Standard queues still send `GroupKey` as `MessageGroupId`, for SQS fair queues.
- **Provisioning:** subscription and instance queues are created with their topic's policy.
- **Results:** the conformance suite passes on the Floci emulator, standard and FIFO. Floci does not enforce the 12-hour visibility rule, policy propagation delays or the in-flight quota (including `OverLimit`), so tests simulate those rules; the transport has not yet run on real AWS. The existing SQSQueue and S3 suites still pass.

### Kafka proof

A Kafka transport was written in `src/Foundatio.Kafka`, with queues and pub/sub through the same contract:

- **Mapping:**
  - queues → a topic read by one consumer group from the earliest offset;
  - durable subscriptions → a consumer group per subscription on the topic, plus the subscription's own topic for retries and sends to that subscription;
  - instance subscriptions → every partition read directly from the end, with no consumer group, so a crash leaves nothing to sweep;
  - dead letters → a topic per source, never compacted and kept at least 14 days.
- **Settlement:** offsets are committed up to the lowest unfinished message per partition, so handling is concurrent. Abandoned messages without a group key are copied with an incremented delivery count; messages with one are released in place to keep group order. Their delivery counts and retry times, and the offsets finished behind a record held for its delivery time, are kept in a compacted `<prefix>.state` topic, so they survive rebalances, closes and (except the last couple of seconds) crashes.
- **Flow control:** a receiver whose buffer is full stops polling, apart from a keep-alive poll, and pauses partitions only past twice its limit, so a backlog drains at the handlers' pace (about 2,800 msg/s with 5 ms handlers, against 40 before). Records held for their delivery time are capped at 10,000 or 16 MB, beyond which their partitions are paused. A group holding 100 records behind its unsettled ones stops the reading; if it doesn't drain to half within 100 ms (at once when its head waits out a retry delay), its later records on the partition are skipped, left uncommitted, and read again in order by a second, groupless consumer per receiver once it drains. A partition skips at most 10,000 records spanning 100,000 offsets (a group that starts skipping skips all it holds past its budget there, which can pass the count by that much but never the span), and a receiver at most 100,000 on all its partitions (about 160 B each, 16 MB). Past a limit it falls back to stop-then-pause and logs the group that skipped the most and the one that skipped the oldest record. After a crash the next owner reads again from the partition's oldest unfinished record, usually the busy group's first unsettled one, which is older than its skipped ones. Records held across many groups are capped at 1,000 or 4 MB per partition and 16 MB in all, with the same rule: reaching a cap stops the reading like a full buffer, and only a partition that doesn't drain to half within 100 ms is paused (at once the next time). Groups are isolated per partition; `Partitions` keeps the broker default, and the first grouped send to a one-partition topic logs a warning (looked up in the background when `CreateEntities = false`). A resumed partition is seeked to its position, because librdkafka otherwise fetches it only at its next 1 s wake-up, and consumers use `fetch.queue.backoff.ms` = 100.
- **Delays:** unlimited, through shared delay-tier topics (1s to 6h) and a forwarder in every process with a receiver, so core never holds Kafka retries in-process. The forwarder only writes to the transport's own topics, drops a record its target keeps rejecting after 12 attempts, and restarts after a failure.
- **Declared:** ordered groups (partition key, and no message of a group handed out while an earlier one is unsettled). Not declared: lease expiration, deduplication. Adding partitions to a topic reorders groups, as documented.
- **Crashes:** a killed consumer's partitions wait for the group's session timeout (45 s by default) before another member takes them. The default is kept, since a shorter one also moves partitions away from a consumer that only stalls; the README shows how to shorten it on both protocols.
- **Subscriptions:** a send to one subscription creates its topics and commits its group's offsets, once per subscription, so publishes made before its first receiver opens reach it.
- **Dead letters:** declares `InOrderCompletion`: offsets can't skip one record in the middle of a topic, so replaying or deleting one dead letter by id throws `MessageBusException`; paging, whole-queue replay and purge work.
- **Results:** the conformance suite passes on the classic and KIP-848 consumer group protocols.

### Service Bus proof

An Azure Service Bus transport was written in `src/Foundatio.AzureServiceBus` (which came into this repo with its history), about 2,100 lines of C# with comments, without changing core:

- **Mapping:**
  - queues → queues named `queue.{name}`, topics → topics named `topic.{name}`: Service Bus queues and topics share one namespace, and a Foundatio queue and topic may share a name (the suite's names test does);
  - durable subscriptions → topic subscriptions; instance subscriptions → a subscription per receiver with `AutoDeleteOnIdle` (5 minutes), deleted on dispose, so a crashed process's is removed by Service Bus;
  - one subscription as a destination → its topic, with the subscription's name in `x-foundatio-to`; every subscription the transport creates has a SQL rule matching messages without that property or with its own name, and an existing one with only the default rule gets this rule instead;
  - dead letters → each entity's own dead-letter queue, with the reason in `DeadLetterReason`; messages Service Bus dead-letters itself arrive with its reason and description.
- **Leases:** peek-lock, with the entity's lock duration reported in `LeaseExpiresAt`, the first transport to use it; it needed no change. The reported lease ends no later than the lock duration after the receive returned, so a local clock behind the broker's can't stretch it; bounding it from the receive's start instead made a message that arrived late in a long poll look expired, so its abandon or dead-letter was refused until the first renewal and a disposing receiver did not release it. Closing a receiver releases its locked messages without counting a delivery, so disposing abandons what it handed out first.
- **Envelope:** the body as-is and headers as application properties, so other Service Bus clients read both; the group key is the session id. Application properties ignore case (they map to HTTP headers), so header names that differ only in case travel in the body envelope; a message id with control characters is replaced and kept in `x-foundatio-id`, and such group keys and deduplication ids become deterministic hashes (the group key kept in `x-foundatio-group`). Headers past 48 KiB of properties (Service Bus allows 64 KiB per message) move into the body, so the open `MaxHeaderSize` capability is not needed here. `MaxMessageSize` is the namespace's limit (256 KiB on Standard, an option for Premium) less 4 KiB for framing, the transport's properties, a retry's copy and the dead-letter reason.
- **Delays:** scheduled messages, unlimited, for sends and publishes. A delayed retry schedules a copy carrying the delivery count and completes the original: in one transaction on a queue, one after the other on a subscription (a transaction would span the topic and the subscription, which needs cross-entity transactions client-wide). Retries under a second are held by core (`MinRetryDelay`).
- **Groups:** `RequiresSession = true` declares `OrderedGroups`. A session receiver accepts sessions as it needs them (at most `MaxConcurrentSessions`) and receives no more of one while a grouped message it handed out is unsettled. Service Bus adds a scheduled message to its session only when it is due, so later messages would overtake it: a delayed grouped message is sent at once with its due time, and the receiver that gets its session holds it and the session, renewing the lock, until it is due. A grouped retry with a delay is held the same way and then abandoned, so it comes back first. Ungrouped messages share eight sessions and are received from them like a queue; a session per message would take an accept each and could not hold the 100 unsettled messages the batch test receives. Accepts and session receives run in the background, several at once, and outlive the receive that started them; a settle wakes a waiting receive. A session closes once a short receive's messages are settled, or after a second with nothing asking for messages. Beyond 256 parked sessions the one due last is closed (held retries are abandoned carrying their due time), and at the limit accepts are limited to 10 a second. Without sessions, receivers declare `MaxConcurrentReceives` = 4 and `ReceiveAhead`.
- **Deduplication:** `RequiresDuplicateDetection = true` declares it. The deduplication id is the Service Bus message id (hashed with the subscription's name for sends to one subscription, since a topic deduplicates for all its subscriptions), the Foundatio id travels in a property, and retry copies always get fresh ids, since an entity that detects duplicates would drop one even with the option off.
- **Provisioning:** queues, topics, subscriptions and rules are created through the administration client; `CreateEntities = false` leaves them to the app and then refuses instance subscriptions and deletes only dead letters. An existing entity in the other session mode is refused.
- **Results:** the conformance suite passes on the Service Bus emulator without sessions or duplicate detection, with sessions and with duplicate detection (66, 74 and 72 tests with the transport's own, none failing); each mode skips the capabilities it does not declare and the count tests, as the emulator reports no counts (the transport returns null there; the mapping is tested against a fake administration client). The legacy queue and message bus suites still pass. The transport has not run on real Service Bus.
- **Emulator gaps:** management on port 5300 only (the transport derives it from a `UseDevelopmentEmulator=true` connection string); `MaxDeliveryCount` at most 10; 50 queues per namespace and 50 subscriptions per topic, so each test gets its own prefix and deletes its queues and topics; `AutoDeleteOnIdle` on subscriptions ignored; runtime counts always zero; deleting a missing queue, or a subscription of a missing topic, answers Bad Request; `NOT EXISTS()` of a bracketed property name does not match, so the rule uses `IS NULL`; an abandon of an expired lock succeeds silently, so the transport checks the lease it knows of first.

### RabbitMQ proof

A RabbitMQ transport was written in `src/Foundatio.RabbitMQ`, beside `RabbitMQMessageBus`, about 1,500 lines of C# without doc comments, also without changing core:

- **Mapping:**
  - queues → quorum queues with `x-delivery-limit: -1`, so RabbitMQ 4 never dead-letters or drops a message on its own after 20 deliveries;
  - topics → fanout exchanges; durable subscriptions → quorum queues bound to them, and a send to one subscription goes straight to its queue;
  - instance subscriptions → exclusive, auto-deleted queues, which the broker removes with their receiver or connection, so there is nothing to sweep;
  - dead letters → a quorum queue per source; dead-lettering sends a copy with the reason and then acknowledges.
- **Connecting:** each of `Hosts` is tried on its own, in random order, with the handshake timeout as the limit, so a node that accepts TCP but never completes the AMQP handshake (RabbitMQ.Client 7.2.2 would wait on it as long as the caller's token allows) costs 10 s by default and is skipped with a log line. Clusters should run `cluster_partition_handling = pause_minority`.
- **Sending:** publisher confirms on a pipelined channel, bounded by `PublishTimeout` (30 s): past it the send fails with `MessageBusException` (the messages may or may not have arrived) and the publishing connection is dropped, so the next send reconnects; queue sends are mandatory, so a send to a queue another process deleted comes back, and the transport declares it again and resends. Topic exchanges route what nobody takes to a discard queue.
- **Leases:** `LeaseExpiration = false`. A delivery stays with its channel; a receiver whose channel closes, or whose consumer the broker cancels after a delete, faults and core replaces it. Automatic recovery is off, so a stale delivery tag can never be acknowledged on a recovered channel.
- **Delivery counts:** RabbitMQ 4.3 quorum queues count a delivery returned by a closed channel (`x-delivery-count`), but not a `basic.nack` with requeue. So an abandon sends a copy carrying the count and then acknowledges, like Kafka's; a peek's release nacks in place.
- **Delays:** the delayed-message plugin does not work on 4.3, so delays use 28 shared levels of fixed-TTL quorum queues (2^n seconds) that dead-letter at least once into the next level's exchange; the routing key spells the delay in binary and ends with the target's name, which a delivery exchange matches exactly. Delays survive crashes with no process running, to 2^28 - 1 seconds at one-second resolution (`MinRetryDelay` = 1s). An at-least-once dead-letter worker stops after 32 unconfirmed messages, so expired messages for a deleted queue or a topic without subscriptions go to a discard queue instead of stalling a level. A delay enters at the level of its highest set bit. Each target gets a landing queue on its first delay (quorum, TTL 0, at-least-once into `{p}.delay.final`, where targets bind by name); `{p}.delay` routes to it, or through its alternate exchange `{p}.delay.final` straight to a target without one (instance subscriptions). A refusing target (a `max-length` policy with `overflow: reject-publish`, or a quorum queue without a majority) holds up only its own landing queue: other delays stay on time, and its own resume 3–6 min after it has room (`dead_letter_worker_publisher_confirm_timeout`, 180 s). An instance subscription that refuses its retries, a target whose landing queue was deleted, or a landing queue under a `max-length` policy still holds a level. One target's delays are capped by its landing queue's dead-letter worker: about 7–8k/s on 4 CPUs, p99 310–450 ms late for a 10k burst. A pre-landing-queue preview broker needs `{p}.delay`'s bindings copied to `{p}.delay.final` before `{p}.delay` is deleted. The inspector lists levels and landing queues in one name-ordered page, sorting by `messages_dlx` only past 500 matches. With `ManagementEndpoint` the transport warns about such policies and about levels or landing queues stuck at 32 or more.
- **Flow control:** the consumer prefetch starts at twice `PrefetchCount`. A quorum queue sends more only as acknowledgements reach it, so once settlements show how long a delivery is held, the prefetch grows to what the handlers get through in about a second, at most 512 and the bodies that fit in 16 MiB; slow handlers keep twice `PrefetchCount` (one handler: 1.8k → 18.5k msg/s; 16: 16k → 63k, within about 10% of the raw client). RabbitMQ counts every unacknowledged delivery against the prefetch and applies a new prefetch only to new consumers, so a caller holding a whole prefetch unsettled, or a grown prefetch, gets a fresh consumer, while the old one's deliveries can still be settled.
- **Dead letters** are a copy then an acknowledgement; AMQP never confirms acknowledgements, so a channel lost in between can leave a duplicate dead letter (226 for 208 poison messages in a chaos run). SQS and Kafka dead-letter the same way.
- **Headers:** AMQP headers, so other clients see them; names the broker or RabbitMQ.Client set (`x-*`, `CC`/`BCC`, and `traceparent`, which the client overwrites while traced) are aliased. AMQP sends properties in one frame (128 KiB by default) and `max_message_size` limits only the body, so headers over 64 KiB move into an envelope in the body: every message within `MaxMessageSize` is accepted without a `MaxHeaderSize` capability.
- **Counts:** passive declares (ready and dead-lettered), or the management API, which also counts unacknowledged messages; `Delayed` is null.
- **Results:** the conformance suite passes on RabbitMQ 4.3.7 and 4.2.5, with delays on and off, as do 14 RabbitMQ-specific tests against the broker (topology, crash cleanup, faults, the discard path, names, foreign messages, headers, conflicts, counts) and 32 helper, codec and option tests. The tests start one broker through Aspire and remove it at the end of the run.

### Azure Storage Queues proof

`Foundatio.AzureStorage` was imported with its history like the other providers, and a transport was written beside `AzureStorageQueue<T>` on `Azure.Storage.Queues` 12.28.2, without changing core:

- **Mapping:** queues → queues; subscriptions → a queue per subscription, marked with queue metadata; a publish lists its topic's subscription queues on every call, uncached, so a subscription opened elsewhere gets every later publish; instance subscriptions → a queue per instance, swept when stale (`InstanceSubscriptionTimeout`, 5 min); dead letters → `<queue>-poison`. Delete clears queues and keeps them, because Azure blocks a deleted queue's name for 30 s or more.
- **Receiving:** Storage can't long-poll, so an empty receiver backs off from 50 ms to 2 s (`MinPollInterval`, `MaxPollInterval`), and sends and retries in the same process wake their own receivers at once. A message from another process waits up to `MaxPollInterval` after a quiet spell (2.06 s measured), and an idle receiver makes about 17 receives in 30 s.
- **Leases** are visibility timeouts. Renewing returns a new pop receipt, which the delivery keeps for its settlement; with a `MessageTimeToLive`, leases are bounded by it. Delays up to 7 days are an initial visibility timeout.
- **Size:** messages are a base64 binary envelope, so the limit is 46 KiB with headers; larger ones throw `MessageTooLargeException` rather than a blob claim-check, whose cleanup would have no owner once a message fans out or is dead-lettered.
- **Auth:** a connection string, or `ServiceUri` plus a `TokenCredential` (or a SAS URI); `UseAzureStorageQueues()` without a connection uses a `QueueServiceClient` from DI.
- **Counts:** `Queued` is Storage's approximate count, which includes leased and delayed messages; `InFlight` and `Delayed` are null.
- **Results:** the conformance suite passes on Azurite 3.37.0 (strict and `--loose`), skipping ordered groups and deduplication, with provider tests for pop-receipt renewals, the poison queue, wake-ups, oversize messages, foreign messages, the stale-instance sweep and TTL. On Azurite, v2 drains 480–630 msg/s at 1.03 Storage calls per message, level with the raw SDK and about twice the legacy queue (2.0 calls per message); Azurite is the bottleneck. Real Azure (RBAC, the 2,000 msg/s per-queue target, name reuse after delete) hasn't been tested.

### SPI refinements suggested by the provider work

Applied in the first round: name validation in the SPI types; the thread-safety, clock, dispose, dead-letter and `DeliveryCount` notes; `GroupKey` round-trip and delayed-publish tests; one-second quiet-period windows in the suite.

Applied in the second round:
- **Separate delay limits.** `MaxDelay` (sends), `MaxPublishDelay` and `MaxRetryDelay`, the last two defaulting to `MaxDelay`. SQS now declares 13 days (emulated) for sends and publishes and 12 hours for retries instead of one compromise value.
- **Size.** `MaxMessageSize` counts body plus UTF-8 header bytes, must hold after the transport's own encoding (binary bodies included), and transports throw `MessageTooLargeException` above it. The suite sends a message exactly at the limit.
- **FIFO batches.** A receive may return several in-order messages of one group. Core handles each group's messages in sequence and abandons the rest of the group if one is retried, so order survives retries. The suite checks that later messages are held while earlier ones are unsettled, and that an abandoned message comes back first.
- **One subscription as a destination.** `MessageDestination.Subscription(topic, name)`, used by dead-letter replay so a subscription's failures are not re-published to every subscriber.
- **Deletion.** `IMessageTransport.DeleteAsync(source)` for removed services' subscriptions, dead-letter purges and test cleanup.

From the Redis update, which also added ordered groups to Redis: the message id, group key and deduplication id count toward `MaxMessageSize` (`MessageSize.Of`) and are capped at 128 characters; group order is send order, delayed messages included; dead-letter sources are not ordered, so peeking shows a whole group; deduplication state may outlive a delete.

From the SQS update, which added FIFO mode: transports may shorten abandon delays to what the broker still allows for a delivery, and receivers left open across a delete may still see older messages (both documented). `MessageSize.Of` stays as it is; instead, a transport reserves framing for at least 100 headers and the dead-letter reason, keeps at least 1,024 bytes of a long reason, and the at-limit tests send 102 headers. Still open: a separate size limit for publishes (SQS accepts 1 MiB, SNS 256 KiB).

From the Kafka transport, as wording only: `CreateReceiverAsync` returns once the receiver can deliver (Kafka waits for its group join, or a first receive such as a dead-letter peek finds nothing); a new subscription gets messages published after it is created; a settle that throws must leave the message to be delivered again, also without lease expiration; `DeliveryCount` may restart after a crash on offset-based brokers, because Confluent.Kafka does not expose commit metadata. Then, also from Kafka: core calls `RenewAsync` about once a second on transports without lease expiration, so a handler whose partition moved is cancelled instead of finishing twice; `MinRetryDelay` lets a transport with coarse delays (Kafka's 1-second tier, SQS's whole-second visibility timeouts) have core hold shorter retries in-process, which stays durable because the delivery is still leased; and `MessageReceiverFaultedException` (or five receive failures in a row) makes core drain, dispose and replace a receiver.

From the Service Bus transport, without contract changes: `LeaseExpiresAt` worked as designed, and session receivers share one renewal per session, since all its messages share one lock. The provider guide now says to keep a queue and a topic of the same name apart where the broker's share a namespace, to check a known lease before an abandon where the broker accepts stale ones, and to abandon on dispose where closing a link does not count a delivery. Still open: core treats names as case-sensitive while Service Bus does not, so names that differ only in case share an entity (the transport documents it; core could reject such names); `ReceiverOptions.LeaseDuration` means nothing on a broker with per-entity locks, so its test class sets `ShortLease` to the entity's lock duration; a delayed retry or delayed grouped message that a transport holds with its group locked costs a session (Service Bus) or memory (Kafka) per waiting group, the same trade-off core-owned holds would face; and `DeleteAsync` never deletes topics, so test cleanup of a broker with entity quotas (the emulator's 50 queues) happens outside the SPI.

From the RabbitMQ transport, nothing changed in core; the friction, for the next round:

- **Release without an attempt.** Quorum queues release a nack-requeued message in place without counting it, but `AbandonAsync` must increment `DeliveryCount`, so abandons copy and acknowledge (a crash in between delivers twice), and a dead-letter peek, which core releases with `AbandonAsync`, nacks in place and leaves the count alone. A release that does not count, the SPI change listed under Not done yet for grouped batches, maps to RabbitMQ's native requeue.
- **Prefetch.** `ReceiverOptions.PrefetchCount` reads as a buffer, and the suite holds 100 unsettled messages on one receiver; RabbitMQ's prefetch caps every unacknowledged delivery and cannot be raised on a live consumer. The provider guide now says a receiver must keep delivering to a caller that holds more.
- **Hold limit without lease expiration.** RabbitMQ closes a channel that holds any delivery past `consumer_timeout` (30 minutes), losing all of the receiver's deliveries. `MaxLeaseDuration` only shortens renewal intervals; a cap after which core cancels the handler, or a per-delivery renewal that resets the broker's timer, cannot be expressed.
- **Headers the client rewrites.** RabbitMQ.Client writes its own `traceparent` and `x-dotnet-pub-seq-no` into the headers it publishes. Transports on traced SDKs need to alias application headers with those names.
- **Uncounted in-flight messages.** Without the management API, AMQP reports only ready messages, so a delivered message is counted nowhere rather than as queued, as `MessageSourceStats` suggests for brokers without in-flight counts.

Not added: a maintenance hook. A transport already runs a timer for instance-subscription heartbeats, and sweeping stale ones from that timer (or on publish) needs no extra contract.

## Messaging semantics

- **One handler model.** `Task HandleAsync(T message, IMessageContext context, CancellationToken ct)`, the same shape as `IJobHandler<TArgs>`; both contexts extend `IHandlerContext` (`Attempt`, `CorrelationId`, `Headers`, `ReportProgressAsync`), so helper code can take either. Return completes; throw retries by `RetryPolicy`, then dead-letters; `context.DeadLetter(reason)` and `context.Retry(delay)` decide without throwing. Manual settlement exists only for transport authors.
- **Send vs publish** is the only topology choice. `AddConsumer` (queue, competing) or `AddSubscriber` (topic; `Scope = Service | Instance`). Sending a type this process only subscribes to, or publishing one it only consumes, logs a warning once per type; a mix-up between two services can't be seen in-process. Instance subscriptions are per topic: an instance handler of N types on N topics opens N, so types routed to one topic (`MapMessage<T>(name, topic: "notifications")`) share one.
- **Registration is checked.** Handler and job classes are registered in DI, so `ValidateOnBuild` fails naming the handler and its missing service. `MessagingOptions` and `JobWorkerOptions` are standard options (`services.Configure<T>`, configuration binding), and handler, subscription and job options may come from a factory over the app's services, run when the host starts. Options that can't apply throw at registration: `SubscriptionOptions` with a `Name` or `Scope` on a consumer, two different option sets for one job, `JobTypeOptions` on a CRON schedule with arguments, `EnqueueAsync` passed `EnqueueOptions` as its arguments. Enqueueing a job this process doesn't run, while it runs others, warns once per name.
- **Service names.** Durable subscriptions are named after the service, so on any transport but the in-memory one the host fails to start when a service subscriber has no `Name` and `UseServiceName(...)` isn't set. The application-name fallback is for the in-memory transport and the test harness only.
- **Shared subscriptions.** A service has one subscription per topic, and the handlers on it share each delivery. Handlers on the same source must agree on `RetryPolicy`, `LeaseDuration` and `MaxConcurrency` (unset differs from set, and policies compare by value, delegates included; `RetryPolicy.Exponential`, `Fixed` and `DoNotRetry` return the same delegate for the same arguments, so policies built from them compare equal); the host fails to start otherwise, naming both handlers. `SubscriptionOptions.Name` gives a handler a subscription of its own, at any scope.
- **Options a transport ignores.** A `GroupKey` on a transport without `OrderedGroups`, or a `DeduplicationId` without `Deduplication`, logs a warning once per message type. `MessagingOptions.RequireTransportCapabilities` makes it throw instead.
- **Names** come from `[Message("...")]`, `MapMessage<T>()`, or the full type name; they are validated to `[A-Za-z0-9._-]`, and collisions throw. Only registered types are deserialized.
- **Routing uses the runtime type**, so `PublishAsync<Base>(derived)` reaches derived subscribers; base-type handlers receive mapped derived types on a shared topic.
- **Unknown types**: skipped on a subscription (topics carry many types); retried then dead-lettered on a queue (usually a rolling deploy). At startup Foundatio registers the concrete types in each handled type's assembly, so derived events from a shared contracts assembly arrive as their own type. A published message also lists its `[Message]` base types and interfaces in `message-base-types`, so a handler for a concrete base type receives derived types from services this one doesn't know. An unknown type whose only accepted base types are abstract or interfaces can't be deserialized: it is skipped on topics with a warning, and retried then dead-lettered on queues.
- **Delays**: native up to `MaxDelay`; longer sends hop (re-sent when they arrive early); longer publishes throw rather than duplicate; a retry delay within 20% under `MinRetryDelay` is lengthened to it; with no native retry delay, or one further under, the retry is held in-process, leased and renewed, and its handler slot (and those of its group's later messages in the batch) goes to other messages, up to 10 holds per slot; past that a hold keeps its slot. Stopping releases held retries at once.
- **Leases** renew from receipt until settlement (by `LeaseExpiresAt` when the transport sets it), including messages waiting their turn in a group batch, at a third of the lease (about once a second, as an ownership check, without lease expiration). A failed or hung renewal is retried within what remains of the lease; renewal stops before a message is settled. A lost lease cancels the handler and skips settlement, and on transports with lease expiration so does a lease no renewal could prove: the delivery is marked lost a quarter of the lease (at most 5 s) before the last proven lease ends, as the job worker does (before, a handler on SQS ran about 3 s alongside its redelivery). A receiver that faults, or fails five receives in a row, is replaced at once: the replacement receives while the failed one's in-flight messages finish (up to `ShutdownTimeout`), then the failed one is disposed, after its unsettled deliveries are marked lease-lost, which cancels their handlers, so a replacement's redelivery of those never runs alongside them. Receive and replacement backoff is capped at 10 s. Deliveries the broker releases on its own (a RabbitMQ channel or connection it closed, a Kafka partition lost or held past `RebalanceGracePeriod`) may be redelivered at once while the old handler runs, until the next ownership check about a second later (1–29 ms of overlap in chaos runs).
- **Concurrent receives**: up to `min(MaxConcurrentReceives, ceil(MaxConcurrency / MaxReceiveBatchSize))` receives run at once and share the handler slots. Only one at a time asks for less than a full batch, and failures of receives in flight together count once.
- **Read-ahead** (`ReceiveAhead`, opt-in; SQS, Redis, Service Bus without sessions): receives stop taking slots and ask for batches of `b = MaxReceiveBatchSize`, or `min(MaxReceiveBatchSize, MaxConcurrency)` with `OrderedGroups` unless the transport declares `OneOutstandingPerGroup` (a receive that breaks that promise has the messages of a group beyond the handler slots abandoned, with an error logged), up to free slots + depth − buffered − requested; a FIFO buffer of whole group sequences gives each message a slot as one frees. The depth `D = min(⌈C·t/s⌉, b·R) + b`, at most `⌊C·H/s⌋`, comes from moving averages of slot time `s` and full-receive time `t` (a full receive that took longer than `H` waited for messages and is not sampled, except as `H` when it is the first), with `H = min(1 s, lease/4)` (the shortest lease among the last 100–200 a receive was granted, so one outlier ages out, counted from the receive's start to `LeaseExpiresAt`, so a lease counted from the request survives a long poll); `D = 0` before both are measured and when `s > H`, and `D` covers at most the buffered messages and as many more as fit in 16 MiB of bodies at their recent size (which follows a larger size at once), so it is 0 for bodies over 16 MiB. At depth 0, and in order, receives take slots as before. Up to `min(MaxConcurrentReceives, ceil(C/b) + 1)` receives run; one that returns short parks the others once their calls return (at least one poll stays open), and each full one unparks one more. Buffered messages are unsettled deliveries renewed from receipt, counted `Buffered` (not `Active`) in `ProcessingStatus`, drained at shutdown, abandoned unstarted at the drain deadline, and dropped unstarted (lease-lost, released by the dispose) when their receiver is replaced. Unsettled ≤ 13 × `MaxConcurrency` + D.
- **Retry decisions** never leave a delivery unsettled: a `RetryPolicy` whose `ShouldRetry` or `Delay` throws dead-letters the message with the policy's error, as the job worker does, and a delivery whose handling throws before settlement starts is abandoned.
- **Execution context**: handlers run in a clean execution context; a processor never inherits its starter's `Activity` or message context (a `SubscribeAsync` inside a request used to leave handlers on that ended request's activity).
- **Settlement off the slot**: a settlement that waits on the broker gives its handler slot to the next message, up to `max(2 × MaxConcurrency, MaxReceiveBatchSize)` per processor; past that, or when it completes at once, it keeps the slot. The message stays in flight until settled (drain, outcome, holds cap), and a group's next message waits for it.
- **Dead-letter failures**: when the transport refuses a dead-letter, the redelivered message retries only the dead-letter, without running handlers again, and health reports it. Reasons are capped at 1,024 UTF-8 bytes.
- **Shutdown**: messaging and jobs stop taking work together as soon as the host begins stopping (`IHostedLifecycleService.StoppingAsync`; a job claimed just then is handed back without running), then drain concurrently for `ShutdownTimeout` (20 s each), then cancel, give handlers 5 s more, and release what remains. Keep `ShutdownTimeout` plus 5 s under the host's `ShutdownTimeout` (30 s) and the orchestrator's grace period. Before, they drained one after the other while each kept taking work, about 50 s in all. Settlement never uses a cancelled token. Buffered messages are handled within the drain; those left at the deadline are released without running their handlers.
- **Hosting**: registering handlers is enough. Every `AddFoundatioMessaging` call accumulates; roles are decided when the host starts, not when a method is called. Disposing the service provider stops processors, the job worker and the scheduler even if the host was never stopped. `AddJobLifetimeService()` counts message processors, the job worker and the CRON scheduler as running work, so a process that runs only v2 work isn't stopped 3 s after start.
- **Sends return ids.** `SendAsync`/`PublishAsync` return the message id, and the batch methods the ids in message order. A `Func<T, MessageKeys>` overload gives each message of a batch its own id, deduplication id and group key, so a failed batch can be retried without duplicating what got through (with `Deduplication`). `Delay` together with `DeliverAt` (or `RunAt`) throws, and application headers can't reuse `KnownHeaders` names. `IMessageClient` has 5 members; the batch overloads without keys are extensions, and `MessageClientDecorator` forwards everything, so a decorator overrides only what it changes.
- **Dead letters** page with `PeekDeadLettersAsync(source, skip, max)` (a page after `skip` costs `skip + max` receives; pages keep order except on SQS) and are replayed or deleted one at a time by id (`ReplayDeadLetterAsync`, `DeleteDeadLetterAsync`, looking through up to 10,000), over the existing receiver SPI; transports declaring `InOrderCompletion` (Kafka) throw for the by-id calls. `IMessageAdmin.GetQueue<T>()`, `GetSubscription<T>(name?)` and `GetSources()` name sources from registrations instead of strings.
- **Tracing and metrics** follow the OpenTelemetry messaging conventions: spans `send {destination}` / `process {destination}` with `messaging.system`, `messaging.operation.type`/`name`, `messaging.destination.name`, `messaging.message.id`, `messaging.consumer.group.name` and conversation id, linked by `traceparent`; instruments `messaging.client.sent.messages`, `messaging.process.duration` (seconds) and the like, each with a unit; Foundatio-specific tags under `foundatio.*` (`foundatio.outcome`, `foundatio.message.type`, `foundatio.source.kind`, `foundatio.job.*`). `docs/guide/monitoring.md` lists every span, attribute and instrument. Nothing allocates for telemetry without a listener.
- **Provider helpers.** `UseRedis`, `UseSqs`, `UseKafka`, `UseAzureServiceBus` and `UseRabbitMQ` (and `UseRedis` for jobs) take options, a factory, a connection string or, for Redis, SQS, Service Bus and RabbitMQ, a connection or clients; `UseSqs()` uses the AWS clients registered in DI, and `UseRedis(string)` registers one shared multiplexer that caches, locks and jobs can use. Option names match across providers (`MaxMessageSize`, `CreateEntities`, `DeduplicationWindow`, `InstanceSubscriptionTimeout`), and transports, monitoring and health checks run on `MessagingOptions.TimeProvider` / `JobWorkerOptions.TimeProvider`. Job stores throw broker errors as `JobStoreException`. They fill an unset logger factory and time provider from DI, and the container creates and disposes the transport or store; a connection from DI stays the app's. A missing `IConnectionMultiplexer` fails host start.

## Job semantics

- **Contract-first**: `IJobHandler<TArgs>` is identified by its argument type, so producers enqueue `new GenerateReport(...)` without referencing the job class. A job without arguments implements `IJobHandler` and gets the same `IJobContext`.
- **Legacy jobs** run through one bridge, `LegacyJob<TJob>` (`AddLegacyJob<TJob>()`, `AddCronJob<LegacyJob<TJob>>`), named after the job class; a failed `JobResult` fails the attempt and a success message becomes the job's message. A `Cancelled` result while the token never fired (a `JobWithLockBase` lock miss) succeeds with its message, as in the hosted runner. `EnqueueAsync<TJob>` and `AddCronJob<TJob>` require `IJobHandler`, and `AddJob<TJob>` rejects an `IJob` at registration, so the bridge can be made `[Obsolete]` together with `IJob`.
- **App view and store record.** `IJobClient` returns `JobDetails`, with `GetArguments<TArgs>()`; `JobInfo` in `Foundatio.Jobs.Store` is the store's record, part of the SPI.
- **Headers and tracing.** `EnqueueOptions.Headers` are stored with the job and passed to `IJobContext.Headers`. Enqueueing under an activity stores its `traceparent` and `tracestate`, and the job's activity continues that trace. `CorrelationId` defaults to the current message's, then the current job's, then `Activity.Current.Id`, as `QueueBase` does.
- **Claim token fencing.** A run's result is accepted unless another worker has claimed the job since, even if the lease expired. The worker also cancels a job shortly before its lease would run out when it can no longer renew it, and records no result for that run.
- **Claims and renewals in bulk.** A worker claims one job per free slot in one store call (`IJobStore.ClaimBatchAsync`; a store without it claims one per call, so a worker on a networked store tops out near one job per round trip). One renewer with one timer per worker renews every running job's lease. `CancelAsync` cancels a job running in the same process at once, and one in another process at its next renewal (up to 5 s).
- **Names come from the arguments' runtime type**, so arguments passed as `object` or a base type run the job for their actual type.
- **The result is authoritative.** A job that finishes successfully succeeds even if cancellation was requested. Cancellation marks it cancelled only when the job stops because of it.
- **Shutdown releases** running jobs without consuming an attempt. Crashes (expired leases) do count, and a job that keeps crashing fails after `MaxAttempts`.
- **Idempotency only when asked**: a caller-supplied `JobId`. Random ids reserve nothing.
- **Concurrency keys.** `EnqueueOptions.ConcurrencyKey`: one running job per name and key, enforced by the store at claim. A blocked job stays queued without using an attempt or backoff and is set aside per key, so it doesn't hold up other keys or names; a batch claim never takes two jobs of one key. The holder keeps its key across a lost lease until it is claimed again, so a slow worker that still finishes never overlaps the next job.
- **Deduplication keys.** `EnqueueOptions.DeduplicationKey`: while a job with that name and key hasn't started, enqueuing again returns it, like `DuplicateDetectionQueueBehavior`; the key is free once the job is claimed, cancelled or deleted. Both keys together give one running and one waiting per key. `IJobStore.CreateAsync` returns the job's id (the waiting job's for a duplicate, null when the `JobId` exists).
- **Retention** is set globally, per job type and per schedule (`RetainSucceededFor`, zero allowed). The worker keeps each schedule run until no scheduler could create it again (the next occurrence, or the misfire threshold if sooner, plus a minute), so exactly-once CRON no longer depends on retention: a 5-second schedule with zero retention keeps about 13 records. The scheduler finds the latest occurrence in the misfire window by binary search instead of listing them all.
- **CRON without leaders or stored schedules.** Every instance computes the latest occurrence within the misfire threshold and creates `cron:{schedule}:{utc}`; the store keeps one. Each schedule is isolated in its own try/catch; overlap is skipped by default, checked against the previous occurrence in the store, so it holds across instances. Schedules are code, so removing one removes it.
- **Cancellation and progress** ride on lease renewal; progress writes are throttled. Message handlers report progress the same way; it goes to the monitor, a span event and a Debug log, never to the transport.
- **Occurrence vs availability.** `JobInfo.ScheduledFor` holds a job's first due time (for CRON, the occurrence). Stores set it at create and never change it; `IJobContext.ScheduledFor` and `JobDetails.ScheduledFor` read it, and `AvailableAt` is the next time the job can run.
- **Store time** is used for leases, availability and retention. Immediate and delayed jobs become available by the store's clock (`CreateAsync(job, availableAfter)`), so a producer 30 s fast no longer delays them; `RunAt` and CRON occurrences are absolute.
- **Succeeded jobs drop their arguments** in both stores and keep the rest of the record until retention ends. Measured: a succeeded job takes about 1.6 KB in Redis, a failed one with 200 bytes of arguments about 2 KB, and an in-memory job about 1.2 KB with its indexes. The in-memory store indexes queued and running jobs by name and due time and finished ones by expiry, so claims and counts don't scan retained jobs; the Redis store sweeps expired jobs in batches of 250 until it catches up (up to 5,000 a second per process), started by claims and queries without making them wait; counts of finished jobs wait for it.
- **Startup gate**: workers, schedulers and message handlers wait for Foundatio.Extensions.Hosting startup actions, however long they take, and do not start if they fail.

## Monitoring

A dashboard sees in-flight work for messages and jobs together, stats for all work, and opt-in progress, without a store write per message (PR #533's broker tracking doubled the I/O on every send and receive, and disagreed with the broker after crashes):

- **Tracker.** Every process tracks the work it runs, always on. A message or job shows as active once it has run past `ActiveThreshold` (1s) or reported progress; a capped buffer keeps recent visible work and every retry, failure, dead letter and cancellation; rolling one-minute buckets over `StatsWindow` (5 minutes) count every outcome and duration per message type and source or job name. Following one item costs about 90 ns and no allocation: the tracking fields live in the handler context. Payloads and headers are never recorded.
- **Snapshots on `ICacheClient`.** `AddFoundatioMonitoring(m => m.UseCache())` makes each instance write a versioned JSON snapshot every `SnapshotInterval` (5s), sooner when visible work changes, with an expiry of three intervals plus a membership entry, so a crashed instance drops out and a stopped one removes itself. Any shared cache works, so no store SPI was added; a hybrid or in-memory cache shows partial data.
- **Backlog.** `IMessageTransport.GetStatsAsync` reads approximate counts from the broker: Redis from the stream, group and lease, retry and delay sets in one script (exact at that moment); SQS from queue attributes (retries waiting out their visibility timeout count as in flight; FIFO has no delayed count); Kafka from consumer lag read without joining the group (no in-flight or delayed counts; a received message stays queued until its offset is committed); Service Bus from runtime properties (locked messages count as queued; subscriptions have no delayed count); RabbitMQ from passive declares (ready messages; delivered, unsettled ones are counted nowhere) or, with a management endpoint, the management API (unacknowledged messages as in flight). A broker that can't tell two states apart counts a message in the nearest one and documents it. `IMessageAdmin.GetStatsAsync` exposes one source. Messages a processor has read ahead count as unsettled: in flight on SQS and Redis, queued on Service Bus.
- **`IWorkMonitor`** reads instances, active and recent work and stats across instances, the backlog of every source they receive from, and job counts per name and state, each cached for one interval however many dashboards poll; `GetOverviewAsync` returns a dashboard page in one call. A process with no handlers or jobs only reads. The dashboard UI itself is not part of this PR.
- Deliveries through `AddLegacyMessageBus` are not tracked.

## Testing and health

- **Whole-app tests**: `services.AddFoundatioTestHarness()` swaps in the in-memory transport and job store and records through internal observers in the client, the processor and the worker, so outcomes are what core decided (completed, retried, dead-lettered, skipped), not transport calls. Waits are signalled by recordings rather than polled by tests. CRON fires only through `TriggerCronJobAsync`, because the misfire catch-up would otherwise run schedules at startup depending on the time of day. `FoundatioTestHarnessOptions.TransportCapabilities` makes the in-memory transport behave like the production one (no deduplication, no ordered groups, delay, batch and lease limits, no lease expiration); the conformance suite also runs against an SQS-standard-like and a Kafka-like in-memory setup. The harness owns the transport, job store and clock whatever the registration order (`Use*` calls do nothing while it is registered), and runs on the system clock unless `TimeProvider` is set, so tests that move the app's clock don't strand leases. It can start paused and process pending work on demand through the real dispatcher and worker (`ProcessNextAsync<T>()` runs one due delivery or job run, the replacement for `QueueJobBase.RunAsync()` in tests, so what a handler sends back and each retry are the next step; `ProcessPendingAsync<T>()` drains; `WaitForIdleAsync()` while paused runs everything and pauses again), override every retry delay (`RetryDelay`), record which handler ran (`HandledBy<T>()`), `Reset()` between tests, and share one in-memory transport and store across hosts. `MessagingOptions.TimeProvider` and `JobWorkerOptions.TimeProvider` set the clocks apps use outside the harness.
- **Health**: each processor, the worker and the scheduler keep their state, when the current run of errors began and the last error. `MessagingStatus` and `JobsStatus` expose it, and Foundatio.Extensions.Hosting turns it into health checks: retried errors are Degraded; a stopped loop, failed startup, or errors lasting past `unhealthyAfter` (5 minutes) are Unhealthy.

## Compatibility

- No existing public type changed. `IQueue<T>`, `IMessageBus`, `JobBase`, `JobRunner` and hosted jobs are untouched, so v13 providers keep loading. ApiCompat against the 13.0.5 packages (all seven) found no breaking change in round 7.
- `AddLegacyMessageBus()` shares the types `IMessageClient` knows (mapped, `[Message]`, handled by a registered handler, or already used): a legacy publish of one also goes to its v2 topic with v2 headers, keeping `legacy-type` as a marker, and a legacy `SubscribeAsync<T>` also opens an instance subscription on T's topic that skips marked copies, so each subscriber on either API gets a publish once and v2 publishes pay nothing for it. Between services, every service must know the type; other types (cache invalidations) stay legacy-only. Once a type's legacy subscribers are gone, `AddLegacyMessageBus(o => o.MigratedMessageTypes.Add(typeof(T)))` in every process sends its legacy publishes once, to the v2 topic as `IMessageClient.PublishAsync` would; remaining legacy subscribers of the type, a base type or `IMessage` read that topic and get each message once.
- `AddLegacyMessageBus()` serves the original `IMessageBus` from any new transport; it passes all 35 tests of the original `MessageBusTestBase`. It runs on a message processor, so its receiver is replaced when it faults and leases are renewed; like the original buses, it handles messages one at a time in order and runs a message's subscribers concurrently. It receives up to 100 messages at a time (or `MaxReceiveBatchSize`), and completes each while the next is handled. `HybridCacheClient` and `CacheLockProvider` run on new transports unchanged.
- `IJob` and `JobBase` work as CRON and on-demand jobs; `[Job(Name)]` names them.
- New names don't collide with v13 code: the job lifecycle is `JobState` (the hosting package has a `JobStatus`), and `RetryPolicy` lives in `Foundatio.Resilience`. `tests/Foundatio.SourceCompatibility` compiles v13-style app code, with Polly and ASP.NET Core imported, against the new packages; it failed on both names before the rename. A file that imports `Foundatio.Resilience` together with `Polly.Retry`, `Quartz` or `Amazon.Runtime` and names a bare `RetryPolicy` still needs an alias; that one was kept.
- Nothing new depends on `IJob`, so v15 can delete the legacy types and `LegacyJob<TJob>` without renaming anything new.

## Not done yet

- SQS's 16 receives and read-ahead have run only on Floci; real SQS may return short batches from a backlog. That would cost twice: a short receive is not full, so it never samples `t` (the remedy is to sample `t` from any non-empty receive that returned within `H`), and `UpdatePolling` resets to one poll on every short return, so a backlog that returns 7-9 of 10 keeps one receive in flight (the remedy is to park only on an empty return, or after several short ones in a row). In-order processors (the legacy adapter) do not read ahead.
- Providers beyond Redis, SQS/SNS, Kafka, Service Bus, RabbitMQ and Storage Queues, plus conformance runs against real brokers in CI. The AWS, Service Bus and Storage Queues transports have only run against emulators, and the RabbitMQ transport only against a single local broker.
- Waking idle job workers in other processes when a job is enqueued. Today it is local wake-up plus a 1s poll. Retention for unread durable subscriptions (Redis warns when one looks orphaned).
- Held messages count as delivery attempts: when a grouped message is retried, the group's later messages in the batch are released and count the delivery. Fixing it needs a release that doesn't increment `DeliveryCount`, an SPI change.
- Mediator mapping onto `AddConsumer`/`AddSubscriber` and `IJobClient`.
- A lease-lost signal from transport to core, so a handler is cancelled as soon as a broker releases its delivery (a closed RabbitMQ channel, a lost Kafka partition) instead of at the next ownership check about a second later. It would cut the overlap with a redelivery to milliseconds, never to zero.
- Job concurrency keys: a limit above one per key, keys shared across job names, and a key selector on `JobTypeOptions`.
- Removing one dead letter by id on Kafka, which would need the transport to record removed offsets. Running the Service Bus control-character id and case-only header encodings on real Service Bus.
- The chaos workload (`tests/Foundatio.Chaos`) runs by hand; Service Bus, real SQS and Redis Sentinel failover haven't been through it.
- Ordering for transports without `OrderedGroups` is not emulated in core: it would only hold within one process, which is worse than an honest "unordered".
- Marking legacy types `[Obsolete]` once providers ship transports.
- One transport per app. Reserved for later, without SPI changes: named transports chosen per message type or queue (`UseTransport("fifo", …)` plus `MapMessage<T>(…, transport: "fifo")`), so one FIFO queue doesn't make every queue FIFO.
- A `MaxHeaderSize` capability and core-owned holds for delayed grouped messages were left until Service Bus and RabbitMQ providers existed. Neither needed them (see their proofs): both move headers that don't fit into the body, Service Bus holds a delayed grouped message with its session, and RabbitMQ doesn't order groups. The SPI can drop `[Experimental]` once the Service Bus transport has run on real Service Bus; until then, providers outside this repo need `NoWarn` FOUNDATIO0001.
